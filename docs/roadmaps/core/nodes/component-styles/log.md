# Log: component-styles

- Repro: `import './todo.css'` in `examples/todo/src/todo.tsx` built with exit 0 and no CSS anywhere. The compiled server module keeps only the imports that the view uses, and a client chunk is an entry that nothing imports a stylesheet from.
- Design: the plugin reads the imports itself (`vite/styles.ts`, `findStyles` in `plugin.ts`). It parses each component file and each script it imports (outside `node_modules`), resolves each specifier through Vite, and keeps the stylesheet ids in import order. A child component's file is one of those scripts, so a parent's set holds its children's. No compiler change: the server module needs no code for a stylesheet, only its URL.
- Build: one emitted client entry per module file, `\0idlip-styles:<file>`, imports the stylesheets, so Vite writes them as assets. `generateBundle` reads `viteMetadata.importedCss` of the entry and of the chunks it imports, writes `styles:<module file>` into the chunk map, and drops the entry from the bundle. A CSS Module has no side effect for the bundler, so the entry re-exports its default (`export { default as s0 }`) with `preserveSignature: 'strict'` so the export stays. Measured: with a bare import the module's rules were tree-shaken out of the stylesheet.
- CSS Modules in client chunks: a binding or list chunk imports `./todo.module.css` for the class object. Two chunks importing the module made Vite emit a shared chunk, which `checkChunkImports` rejects and which would be a second request on a click. Fix: `resolveId` turns that import in a chunk into `\0idlip-names:<file>@<chunk>`, whose `load` copies the code of the loaded module (`this.load`). Each chunk holds its own copy of the object, and no chunk imports a stylesheet. The hash is the same in the server render and in the chunks (checked in `test/styles/build.test.ts` and in e2e).
- Server: `STYLES_KEY` and `renderStyles` in `server/styles.ts`. `collectModules` in `render.ts` unions the `styles` of the root and of each child module and keeps the key out of `urls`, so it is not in the state script. `writeFirst` in `stream.ts` puts the links first in the added head output, before the listener and the preload links.
- CSP: `style-src 'self' 'nonce-<n>'` is in the default policy. A `style-src` in `extend` replaces it, so `extend: { 'style-src': ["'self'"] }` of existing apps still works.
- Dev: the links point at the files Vite serves (`/src/todo.css`). A request that accepts `text/css` gets the CSS (Vite adds `?direct`), and Vite's hot update changes a `<link>`. Checked with Nitro and with the plugin middleware (`hot` and `hot-fallback` projects). Dev client chunks import the real CSS Module, so Vite also injects a `<style>` with the same rules next to the link.
- `pnpm check` is in the brief but the root has no such script. I ran `pnpm build`, `pnpm exec oxlint --type-aware`, `pnpm format:check`, `pnpm typecheck` and `pnpm test`.
- `todo.tsx` first used the module on the `<li>`. The website demo reads `<li i-a=...>` from the built page and failed the build, so the module class moved to the count `<p>`, which the same click patches.
- A `style` attribute is blocked by `style-src` with or without a nonce, so the string form of `style` (decision 3) needs `style-src-attr 'unsafe-inline'` under `csp: true`. The docs say so. I did not add that directive by default, since it loosens the policy.
