## Brumate decisions not to copy

- **Load all page code at start.** Brumate's own cold dashboard click at 150 ms RTT is 456 ms (115 kB at 1.6 Mbit/s, `perf-pass-0.4/outcome.md`) and 480 ms in the idlip harness. idlip's is 216 ms. JS before `load` grows 12.7x from 10 to 1,000 widgets for brumate and stays flat at 4.7 kB for idlip (`benchmarks/README.md`, Scale). Take the preload links (row 1), not the eager load.
- **Merge chunks by a size threshold.** Brumate can merge because it loads everything. idlip's thesis is that a click loads the handler chunk and the binding chunks of its write set (`GOAL.md`), and `spike-chunk-merge` measured parallel loading as fast as one merged file.
- **Compile-time state graph and `$memo` ranks.** Brumate's update queue (`drain`, `pass`, `settle`) is 2.1 kB gzip and exists because components share signals. idlip updates are data with a write set. Nothing to port.
- **One page-wide bundle per root component.** It needs the whole component tree known at build time and breaks the lazy per-handler chunks.
- **Marker and `b-b` index scheme.** Brumate indexes elements with `b-b` attributes and a marker index. idlip uses `i-a` and comment markers read at the first event. Take the idea in row 6, not the format.
- **Unify the server and browser render paths.** Brumate tried ("values-spike") and missed every gate: todos +312 B gzip, rows create script 1.43x, divergences 38 to 42 pages. It kept both paths (`values-spike/outcome.md`). Expect `cloned-templates` to add a second output and plan the differential test for it.
- **Drop idle preload in favor of eager load** (`c648e223`). The reason was that all code loads at start, which idlip does not do. Row 1 re-examines it.

## Contradictions with current idlip nodes

- `cloned-templates` (must, size L) expects the create gap to close. Brumate's own steps saved 2.7 ms of script on top of a batched parse, and brumate's total create script is 2.95 to 6.3 ms against idlip's 12.9 to 16.5 ms. Guess: the template change gives 3 to 6 ms, so its acceptance can fail inside the noise (33.9 to 41.8 ms). Profile the non-parse part of idlip's script (row 2 and `getRowScope`, `findNodes`, `await`) before the L-size work.
- `cloned-templates` says "an existing differential test, or add one". There is none in `packages/idlip`. Row 8 is a missing prerequisite.
- `perf-list-create` found that one parse for all rows is within noise, while brumate batched its parse (`5487ee44`) and then still saved 2.7 ms with clones. Both are consistent: the clone avoids the parse itself and the per-row marker walk. A batched parse alone does not.
- `spike-chunk-merge` recommends "no merge threshold" from one todo module and first-click time only. It did not measure the dashboard dist size (364 files), which brumate's merge cut by about 3x. This does not change the recommendation, since `GOAL.md` forbids extra chunks on a click, but the dist-size cost is unmeasured.
- `perf-from-bench` treats `renderPreload` as "a note, not in the main table". Brumate's benchmark counts its preload links in the main numbers (0 requests at the first click). The README table makes idlip look 3x to 4x slower on first click against numbers brumate gets with a different loading choice. Row 1 proposes reporting both.
- `prefetch/outcome.md` left `renderPreload` unwired in `examples/todo` (no typed `manifest` export). No later node wires it, so row 1 depends on that typed export. Confirm with `docs-platform` or `deploy-skew` owners (not checked).

## Gotchas

- Brumate's `docs/performance.md` "Templates" says cloning was "measured and not done" (2026-10-24). The same author did it on 2026-10-25. Read the commit log, not only the notes.
- Brumate numbers move with load and machine. Its create 1,000 rows is 34.6 ms in `perf-pass-0.4/outcome.md` and 22.1 ms in the idlip harness. Compare ratios inside one run.
- `bench-rows/outcome.md` marks most rows-loss causes as guesses. Row 2 inherits that. Profile each operation before building, as `perf-list-kept` already says.
