# Debate: Pick idlip's surface language (TS subset, own Elm-like language, hybrid .idlip syntax compiled to typed TS, or brumate-style markup without script/style blocks) so the todo app resumes with one handler chunk plus changed binding chunks, at the lowest total cost

## Settled structure

- P1: Fix the hole grammar before the surface syntax. Holes, attribute values and event payloads accept only: model/loop-variable paths, literals, comparison and boolean operators, ternary, template strings, and calls to imported helpers marked pure. No closures, no assignment, no statements. Every frontend (JSX or markup) parses into the same view-ir, so the choice of shell no longer sits on the must path. (0 must nodes added; spike-view-analysis and compile-view-analyze shrink from arbitrary-JS walks to a closed grammar)
- P2: Ship option A for the todo-resumes milestone: *.idlip.tsx with JSX, oxc enforcing P1's grammar, plain TS model/messages/update. jsx-types stays as typing for the shell; the todo app reaches 'one handler chunk plus changed binding chunks' with no new parser, Volar plugin or editor extension. Zero new tooling nodes before the contract gate. (8 must nodes touched (jsx-types, spike-view-analysis, compile-view-analyze, compile-update, plus the existing 4), no additions)
- P5: Keep update handlers as TS in every option and make write-sets and update-ops the single analysis for them. A handler body restricted to the same pure core (spread, property write via spread, array methods push/filter/map with literal-path predicates) lets the compiler derive the write set; the outline nodes write-sets, update-ops and keyed-paths stay in the roadmap, none grows. Do not move handlers into a new syntax, since only that part of option B would help. (3 outline nodes unchanged (write-sets, update-ops, keyed-paths))
- A2: Reject B (own Elm-like language and checker). The only gain is a handler language that makes write sets trivial, but 0003 gets that inside TS. Cost: HM inference, errors and editor work took Elm years, and idlip would lose npm types, model/helper reuse and oxc. (3 months minimum (estimate; brumate needed a month for a TS-hosted language with 64k lines))
- O7: Cheapest structure: A with P1's closed grammar for todo-resumes and 0.1, and make the view-ir contract the only seam. Park D as one outline node with a measured trigger: build it only if P1 violations or JSX noise show up in examples/todo and one more app. No new must node, no file-type tooling, no spec rewrite. B is dropped, as A2 says.
- P6: Amend P1 with a helper rule, no marker and no purity proof. A helper call is legal when the callee is an import or module-level function whose arguments are all in the closed grammar (a closure argument is a compile error). Its hole paths are the union of the argument paths, as 0001 already says. A whole-model argument is a warning. If the helper body is one return expression in the closed grammar, the analysis inlines it for exact paths, the same as partials. A hidden dependency in a helper (module state, Date.now) can only cause a stale binding, so dev mode re-evaluates each patched hole from the new model and reports a mismatch as an error naming the hole. The view-ir contract gets one line, helper: 'args' | 'inlined'. (1 contract line in view-ir.md; one dev-only check in the errors node)
- P9: Roadmap and contract changes under the settled structure (A, closed grammar, D parked). Contracts: view-ir.md gains helper: 'args'|'inlined' and the closed-grammar list; core-api.md and 0002 stay unchanged (defineModule, update before view, view(m, msg)). Nodes: jsx-types, compile-update, write-sets, update-ops, keyed-paths, dynamic-paths unchanged; spike-view-analysis and compile-view-analyze take the closed grammar and helper rule as scope and report violations as errors; errors node gets the dev hole re-evaluation check; one new outline node markup-frontend (could, parked). Net: 0 new must nodes, 1 outline node. (0 must nodes added)
- O9: Cheaper and sound check for P6: run it in the must node testing-mount, in Node tests, not in the browser. After each message in a test, re-render the whole view on the server from the new model and compare it with the DOM the patcher produced. This catches stale holes from any cause, needs no dev chunk loading, and uses code that already exists (ssr-render plus patch-bindings). Also make a whole-model argument to a helper a compile error, not a warning: its path set is the root, so the hole rebinds on every patch and defeats the goal.
- O11: Amend my O7 trigger to something a script can read: the compiler tags each closed-grammar diagnostic with a rule id, and the trigger counts only the ids that block syntax removes by construction (list rendered by .map instead of <For>, && or ternary instead of <Show>/<Switch>, missing or non-path key). D is built only if those ids total at least 10 across the todo app, one form-heavy app and agent-written drafts of both, and agents fail to fix them in one retry. Needs only an id field on diagnostics in the errors node. Drop the token-percentage test.

## Rejected

- P3: After 0.1, add a brumate-style markup shell (option D) as a second frontend: .idlip files with only markup (#if/#for/#switch blocks, attribute value forms, on* events), compiled to typed .ts by a toTypeScript() emitter so tsc checks it. Reuse brumate's grammar.md and Volar wiring instead of designing again. Reason to do it: #for/#if blocks make the key and the branch structure syntactic, which removes keyed-paths and dynamic-paths guesswork from JSX <For>/<Show> call analysis.. Why not: O1 measured brumate's parser and analyzer at 4348 lines beyond the 2-week tooling route, and O2 shows the shell cuts no node; O7's park with a trigger replaces it (by O1, O2, O3, O4, O7)
- P4: Replace brumate's <script> with nothing: a markup file holds only an import header and one 'view(m: Model)' signature line, because model, messages, update and helpers live in plain .ts (option C split). That keeps handlers, which need write-set analysis, in files oxc and tsc already own. Replace <style> with an imported sidecar stylesheet (import './todo.css') that the compiler scopes, so CSS tooling and chunking apply unchanged.. Why not: conceded in P7 on O3 (by O3, O4, P7)
- A1: Cheapest path: A only, forever. Add one editor aid, a tsc language-service plugin that reports P1 violations as diagnostics (no new file type, no emitter). Total new code about one oxc visitor plus a ~100-line plugin; the brumate-style shell is never built unless the todo's keyed lists show JSX <For> analysis failing.. Why not: O6: diagnostics already come from the compiler through the Vite plugin and a check pass; a language-service plugin duplicates them (by O6)
- P8: Park D as one outline node, markup-frontend (priority could, milestone later, provides view-ir). Build trigger, measured with a script over examples/todo plus one more app (a form-heavy one, written after 0.1): D is worth building only if both hold. (1) Token count of the view bodies (oxc tokens) is at least 25% lower when rewritten in brumate block syntax, since D must save more than its upkeep. (2) The compiler's closed-grammar diagnostics log at least 3 distinct JSX-shape errors per 100 view lines that block syntax makes unwritable. If either fails, D stays parked. Cost cap to compare against: brumate's parser 1140 lines plus analyzer 3208 lines (O1), so D must pay back about 4.3k lines of upkeep.. Why not: O10: the token and per-100-line test is not measurable as stated; O11 replaces the trigger, keeping the parked markup-frontend node (by O10, O11)
