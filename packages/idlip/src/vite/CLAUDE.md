# vite

- `features.ts` replaces `__IDLIP_HAS_*__` as text, one literal per line, with `map: null`. Keep line counts the same. Why: there is no source map for the replacement.
- The plugin compiles a `.tsx` file only when a `modules` glob matches it and it holds a function component. Any other `.tsx` file goes to Vite untouched. Why: entries and helper files in `src` are plain TSX.
- A component outside `modules` warns, and rendering one as a child fails the build, both naming `modules`. Do not compile it silently. Why: it would run as plain JSX.
- A chunk URL comes from the bundle chunk whose `facadeModuleId` is the chunk id, never from the chunk name. Why: modules of the same file name in two folders emit chunks of the same name.
- Chunk kinds are `handler`, `binding`, `list`, `task`, `source`, `try` and `view`. A new kind needs `parseChunkId`, `listChunks` and `getChunkFile` (`../core/format.ts`) together. Why: a kind that one of them misses fails only in the build.
- A flag is on from a detector in `DETECTORS` (`features.ts`) that reads the compile result, such as `manifest.fallback`. `HAS_SKEW` is the exception: the plugin option `skew` (default on) sets it through `getDefines(on, skew)`. Why: skew has no manifest sign. A detector must read everything that needs the loader code (`HAS_KEYED` reads group paths only: see `keyed-writes`).
- Skew retention keeps the files of the previous build and deletes older ones through `<outDir>/.idlip/builds.json`, with `emptyOutDir: false` for the client environment. It never touches `publicDir` files. Why: a page cached from the last deploy still needs its chunks, and a page two builds old recovers by reload.
- The plugin resolves `idlip/helpers` to the virtual module `\0idlip-helpers` (`printHelpersModule()`), and `generateBundle` puts the URL of its chunk in the chunk map under `helpers` (`HELPERS_KEY`), which `render()` keeps in the state for the loader. `checkChunkImports` allows that one shared file. Why: one file for every helper, preloaded by the loader in the first click's round trip. When one chunk alone uses helpers, the bundler inlines the module and the key is absent.
- The plugin resolves `idlip/templates` to `\0idlip-templates` (`printTemplatesModule`), and `generateBundle` writes its file under `templates` (`TEMPLATES_KEY`), unless the bundler put it in the helpers file. The loader and `renderPreload` load it with the helpers. Only a build shares templates (`findSharedTemplates`); `vite dev` serves each chunk with its own copies, so HMR needs nothing more. Why: the first click stays one round trip.
- `build.js` is served with `Cache-Control: no-store` or a short max age, and the `skew` option documents it. Why: a cached copy hides a new deploy. It is not a chunk: `listChunks` and the chunk map skip it, and the chunk map has the extra key `build`, which `render()` moves to `i-build`.
- `hot.ts` sends `idlip:hot` for the client environment only and `full-reload` for a module that does not compile. Why: the ssr environment keeps Vite's default handling.
- A file has one `CompileResult` and one or more components. Read them with `listCompiled(result)`, never `result.manifest` alone. A named component's chunk id puts `<Name>.` before the kind, and its files are `<file>.<Name>.<kind>.<name>.js`. Why: a loop over `result.manifest` misses the chunks of every other component.
- The loader URL travels in the chunk map of each server module under `loader` (`LOADER_KEY`): the built file in a build, `<base>@id/idlip/client` in dev. `render()` drops it from the state script and returns it as `RenderResult.loader`. Why: the server reads no manifest and no file, and a Vercel function or a Worker finds the URL in its bundle.
- The dev middleware of the plugin calls the `fetch` of the default export of `entry`, and stands aside when `config.plugins` has a plugin named `nitro:main` or the `server` option is `false`. Why: Nitro runs the ssr environment in its own worker, so the plugin's runner is not runnable there, and both would answer the page (measured: every dev page was a 500).
- The dev loader module imports `/@vite/client` before `idlip/client`, so no page needs markup for HMR and `transformIndexHtml` is not used. Why: the page of Nitro is not run through it. The e2e `hot` run (Nitro) and `hot-fallback` run (plugin middleware) read `idlip:hot` over the socket.
- An edit of a document component that changes the shell, the markup from `<html` to the end of the `<body ...>` tag (`changesShell` in `hot.ts`), sends `full-reload` and not `remount`. Why: a remount swaps `<body>` only, so a changed `lang` or head would not show.
- Nitro empties `.output/public` on each build, so `keepBuilds` keeps no files of the previous build, and it serves `assets/` as `immutable`, so `build.js` needs a route rule. Why: both measured with `nitro@3.0.260903-beta` (see `website/docs/deploying.md`).
- A stylesheet reaches the page through one client entry per module file (`\0idlip-styles:<file>`) that imports the stylesheets its import graph reaches (`findStyles`). `generateBundle` writes their URLs under `styles:<module file>` and drops the entry. A client chunk never imports a stylesheet: a default import of a CSS Module in a chunk becomes a class object written in the chunk (`inlineNames`; any other import form becomes `\0idlip-names:`). A chunk must not import a module of its own for it, since the bundler then moves the chunk into a common chunk and leaves a stub. Why: a shared module is a shared chunk, which a click would load, and a bare import of a CSS Module is tree-shaken, so the entry re-exports it.
- A dependency of the app whose `package.json` has `idlip: { version: 1, dir }` is a component package (`packages.ts`, `readPackages`): the plugin compiles its `.tsx` files, and adds it to `ssr.noExternal` and `optimizeDeps.exclude`. Its module id is `<name>/<path in the package>` (not `/`-rooted), its chunk files start with the package name, and dev serves its chunks at `/@fs/<file>`. A chunk that imports a package component's view imports the module id, which `resolveId` maps to the file. Why: ids must be the same wherever the package is installed, and two packages may both have a `button.tsx`.
- `load` of a chunk id in the client environment calls `checkServerOnly` (`server-only.ts`), in a build and in `vite dev`: it fails when the chunk's own imports, walked through your files, reach `node:` or a bare built-in, or when the chunk or a walked file reads an `import.meta.env` key outside `envPrefix`. It skips `idlip` and `idlip/*`, files under `node_modules`, virtual ids and non-scripts. Why: the runtime and dependencies are not user code, and the server render is not checked because its code never reaches `load` of a chunk (the compiler copies into a chunk only the imports and module-level bindings it uses).
