# compiler

- A bound value of a URL attribute is wrapped in `safeUrl$` (`core/helpers.ts`), decided by `getUrlKind(tag, name, target)` in `core/url.ts`. A new URL attribute goes in `URL_ATTRS`, a new element-specific case (a frame, an animation target) in `getUrlKind`. Why: the compiler wraps only the listed names, and a value a browser runs as a script or a document must not come from data. A literal in source is not wrapped, since the author wrote it.
- Raw HTML reaches the page only through `trusted(...)` imported from `idlip`: `html=` and a bound `srcdoc`. Anything else is `html-trusted` or `srcdoc-trusted`. Why: `trusted` is the one place the author vouches for markup.
- A chunk imports its runtime helpers from `idlip/helpers` (`HELPERS_MODULE`), never a copy. The Vite plugin serves that module from `printHelpersModule()`, and the loader loads it with the first chunk (`helpers` in the chunk map). Why: copies put the same helpers in every chunk (dashboard dist 150.4 kB gzip with copies, 104.0 kB with the shared module), and the loader's parallel load keeps the first click one round trip.
- A template that more than one chunk renders is declared once in the virtual module `idlip/templates` (`TEMPLATES_MODULE`), as `export const t<hash>`, and each chunk imports it (`import { t<hash> as templateL3$ }`). Codegen takes the hashes from `GenerateOptions.shared`, and the Vite plugin finds them: it compiles every module once, counts the chunks per hash (`Module.templates`, hash of namespace and markup), and compiles again with the set. A template of one chunk stays in that chunk, and a build without the option (dev, tests, the REPL) declares every template in its chunk. Why: dashboard had one row template in 100 chunks, so 99 extra copies and parses, and a per-hash file cannot be preloaded within the loader budget, so all shared templates share one file that loads with the helpers.
- A helper of `idlip/helpers` (`core/helpers.ts`, `core/dynamic.ts`) holds no comment in its body and no name from outside its own text. Why: `printHelpersModule` writes the module from each function's `toString()`.
- A chunk imports a child's view by name (`import { init as $init_Row, render as $render_Row }`), not as a namespace. Why: the view is also an entry, and a namespace import made the bundler emit each view twice (an entry that re-exports a second file).
- A helper ends in `$` (`setAttr$`, `safeUrl$`, `track$`, `getRows$`) and is listed in `HELPER_NAMES`. A module-level author name equal to one is `module-reserved-name`. A local that generated code declares starts with `$` (`$after`, `$e`, `dynamic$`, `lists$` and the cloned templates `template<kind><id>$`, such as `templateL3$` and `templateC4_0$`, are the module-level exceptions that end in `$`). Why: a generated name must not collide with the author's.
- Region, block and boundary ids count on their own counter (`e` regions from 0), so adding a `<Try>` does not move the ids of lists, conditions or events after it. Why: golden fixtures and chunk names depend on ids.
- A change to a chunk's exports rewrites the goldens (`UPDATE_TRY=1 pnpm vitest run test/try`, `UPDATE_NESTED=1 pnpm vitest run test/compiler/view/codegen/nesting`, and the fixture tests). Why: goldens compare the whole chunk.
- Every client body clones a template (`view/codegen/template.ts`, `clone$` in `core/helpers.ts`): rows, branches, child views, catch views and regions, with nested blocks, children, `<Try>`, `<Subscribe>`, `<Head>`, global listeners, SVG and MathML, text elements, static and empty bodies. The only markup a chunk parses is the value of `html=`; `test/compiler/view/codegen/string-render.test.ts` reads the chunks of every fixture, subject, example and benchmark app for it. Why: the user decided (2026-11-22) that only raw HTML content stays a string, and a parse per row was half of create's script time (15.0 to 7.2 ms for 1,000 rows).
- The clone must hold the nodes the server's HTML parses to, markers included. A block inside a body is a marked comment (`<!--c<id>:x<n>-->`, `<!--/lx<n>-->`, `<!--n:x<n>-->`, `<!--e<id>:x<n>-->`), and the body's writes clone the block's own templates next to it. A new node kind needs a write that matches the HTML and a differential subject. Why: the patcher, `readRows` and the differential test read cloned and server nodes alike.
- Where the parser treats text its own way, write what a browser reads from the server's markup, not what the source says. A `textarea` or `title` hole sets the element's text (`textContent +=`, after the newline the server and the template write first in a textarea). In a `pre` or `listing`, the parser drops a newline that starts the text: a leading run of static text and unbound holes becomes one text node whose write drops it, and raw HTML in a `pre`, `listing` or `textarea` drops it from the value. Why: the server's markup stays as it was, and the clone matches Chromium (checked by a probe). happy-dom keeps that newline, so `src/testing/compare.ts` drops leading newlines of a `pre`'s first text on both sides.
- A `<template>` element's content (an author `<template>`, a `<Head>`) clones from its own template and the write appends it to `.content`. Why: the walk of `clone$` does not enter template content, so marks there are not found.
- A component other than the main one (the default export) has the module id `<file>#<Name>` and a module record `$<Name>` (`manifest`, `chunks`, `uses`, `default`) in the server module. `selectComponents` (`view/codegen/components.ts`) picks the components. Why: the default export keeps the chunk names of a one-component file, and a parent imports a named child by its record.
- A bound text hole that is the only child of an element (`getFilledHole` in `view/codegen/plan.ts`, `plan.filled`) has no `<!--t-->` markers: its id goes last in the element's `i-a`, its binding is `a<id>` and `setText$` sets the element's text. Not in `script`, `style`, `textarea`, `title`, `pre` or `listing`. The server render (`html.ts`) and the template (`template.ts`) both read `plan.filled`, and a dynamic hole records its reads under `a<id>`. Why: rows SSR HTML 362089 to 336089 B (gzip 24331 to 23928 B) with no loader change (`text-anchor`). A `pre` drops a leading newline in the server's markup that a clone keeps, and happy-dom cannot show it.
- An event arrow compiles to an event function, `export function $e<n>($e, $c, scope)`, appended to the handler chunk of the first handler it calls (`view/codegen/events.ts`, `emitSites` in `chunks.ts`, `sites.ts` joins it). The attribute is `on:<event>="$e<n> <modifiers>"` and binds nothing. `$e` is the event, `$c` the element (`e.currentTarget` prints as `$c`). A row value is read from the DOM rows with `getRows$` and the model the DOM shows (`rendered`), so it is the row the user clicked. Only message props of a stateful child, a forwarded message prop and a `<Try>` reset stay data (`on:<event>='["tag",[...]]'`, no placeholders). Why: the HTML no longer carries payloads, an arrow may branch and call several handlers, and the first click still loads the handler chunk and its bindings only.
- `compile()` joins the sites into the handler modules with `joinSites`. Code that calls `generate` and `compileHandlers` itself must do the same (`test/compiler/view/codegen/nesting.test.ts` does).
